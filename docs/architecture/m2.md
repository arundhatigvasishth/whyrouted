## 1. The bet: pure strategies behind a thin engine

> PRD §5.3: "Pluggable strategy interface so round-robin, least-loaded, and
> latency-weighted can be swapped and compared live, including via MCP tool
> call, not just config."

**Verdict: correctly implemented.**

- `RoutingStrategy` (`src/routing/types.ts`) is `pick(candidates, weights) -> id | null`
  and nothing else. Strategies do no I/O, never touch the registry or adapter,
  and never mutate their input. They are unit-tested against hand-built
  `ReplicaState[]` fixtures with no HTTP anywhere (`test/routing-strategies.test.ts`).
- The engine (`createRoutingEngine`) is the only piece that joins the parts: it
  reads a fresh registry snapshot, filters to `healthy`, reads the active
  strategy and weights from `RoutingConfig`, and delegates the pick. It holds
  one strategy instance and rebuilds it only on a name change, so a stateful
  strategy (round-robin's cursor) survives across requests.
- `RoutingConfig` is a mutable in-process holder with getters the engine calls
  every request and setters that re-validate. The setters have no in-process
  caller yet (see deferral 3), but the seam the M5b MCP tools plug into is real
  and tested (`test/routing-config.test.ts`).
- `RouteResult` is a tagged union deliberately shaped to grow a rationale field
  in M4 without a breaking change.

The split means routing logic is fully testable without a socket, and a new
strategy is one new file plus one registry entry. That was the goal.

## 3. Leakage check: did any later-milestone concern get built in?

Grepped `src/routing/`, `src/api/`, `src/main.ts` for `retry`, `failover`,
`decision`, `mcp`, `fallback`, `score ... log`, `rationale`, `reason`.

**Every hit is a comment pointing forward** ("M2 has no failover, that's M3",
"the M5b MCP tools are the other writers"). **Zero failover / retry /
decision-log / MCP code exists.**

- `/route` returns `502 replica_request_failed` on a failed `sendRequest` and
  does not retry. That is the correct M2 behaviour: the retry-against-next-best
  loop is M3 (PRD §5.4, and the "up to 2 retries" open question).
- The `no_routable_replica` vs `no_healthy_replicas` split exists so M4's
  decision log can record *why* a request was not served, but no logging is
  wired now.
- The engine's local variable is named `decision`. It is a `RouteResult`, not a
  decision-log record. Harmless, but worth not confusing in M4.

## 4. Known deferrals: carry into M3 / M4 / M5, do not fix now

1. **`sendRequest` still throws a generic `Error` on non-2xx** (M1 deferral 2,
   now live). `/route` is the first caller and it turns every failure into one
   `502 replica_request_failed` body. M3's failover needs to tell retryable
   (503, timeout, connection refused) from non-retryable. The adapter will need
   typed or coded errors then.
2. **`RegistryStore` is still synchronous** (M1 deferral 1, unchanged). First
   real need is M5a. The engine's `getSnapshot()` call would grow an `await`
   with everything else.
3. **`RoutingConfig` setters have no in-process caller.** `setStrategyName` and
   `setWeights` are implemented and tested, but only `WR_ROUTING_STRATEGY` /
   `WR_LOAD_WEIGHT` / `WR_LATENCY_WEIGHT` at startup feed the holder today. M5b's
   `set_routing_strategy` and `set_scoring_weights` MCP tools are the callers.
   This mirrors how M1 shipped `sendRequest` before anything called it.
4. **Latency-weighted is not yet meaningfully different from least-loaded.** The
   health probe measures the round-trip of `GET /health`, which returns
   immediately; only `/infer` sleeps the synthetic latency. So `runtime.latencyMs`
   is near-equal across the fleet and the load term dominates the score. To
   compare the strategies for real (PRD §5.3), either the health probe needs to
   exercise a realistic latency path, or the registry needs to record actual
   `/infer` round-trips. Flagged for M3 or a routing-quality task.
5. **Round-robin's cursor grows unbounded.** `cursor += 1` with no modulo reset.
   Irrelevant at any realistic uptime, `cursor = (cursor + 1) % 1e9` closes it.
6. **`RouteResult.strategy` is typed `string`, not `StrategyName`.** Cosmetic
   tightening, recorded in the contract sign-off.
7. **`src/config.ts` imports `STRATEGY_NAMES` from the routing module,** which
   pulls the three strategy factory modules into the replica launcher's import
   graph. No cycle, tiny cost, noted in the contract sign-off.

## 5. Success metrics (PRD §8): status

| Metric | Target | M2 status |
|---|---|---|
| p99 routing overhead | < 10ms added per request | **Not measured.** The engine does one snapshot copy + a filter + an O(n) pick over ~4 replicas, expected to be sub-millisecond, but there is no benchmark. Needs a measurement task in M3. |
| Load distribution | No replica > 1.5x median utilization under steady load | **Not validated.** `test/integration/m2.test.ts` uses the deliberately uneven K7 profiles and confirms least-loaded concentrates on the lightest replica, which is correct behaviour but the opposite scenario. A load test with even profiles is a follow-up. |

Both are measurement tasks, not design gaps. The routing path is in place; what
is missing is instrumentation.
