# M4 Architecture Review

**Reviewers:** Junaid Pathan (draft), Arundhati Vasishth (pending)
**Date:** 2026-09-24
**Purpose:** Walk the decision-log seam before M5. Confirm every `POST
/route` request produces a full, queryable record of its own routing
rationale, that `RoutingStrategy.pick()`'s frozen contract genuinely held

## 1. The bet: visibility without reopening the frozen interface

> PRD §5.5: "every routing decision writes a structured record: request ID,
> timestamp, chosen replica, the full candidate set with each one's score
> inputs at decision time, and the reason for any exclusion."

**Verdict: correctly implemented.**

M3 froze `RoutingStrategy.pick()` specifically to keep strategies ignorant of
retry exclusion (`docs/decisions.md`, 2026-09-08). M4's whole design bet was
that visibility into what a strategy already computed could be added without
touching that boundary at all:

- `score()` is a genuinely separate method, called by the engine alongside
  `pick()`, not a parameter added to `pick()`. Read-only, does not advance
  round-robin's cursor, does not influence what `pick()` returns. Verified by
  N7's property test (`test/routing-strategies.test.ts`), which checks the
  candidate `score()` ranks lowest is always the one `pick()` actually
  returns, for all three strategies, across five candidate sets including a
  tie.
- The engine, not any strategy, owns exclusion. `ExcludedCandidate` is built
  entirely in `engine.ts` from the registry snapshot and `opts.exclude`,
  before either `score()` or `pick()` is called. This is the same boundary
  M3 drew for `exclude` itself, extended to the observability path.
- The existing M2/M3 strategy test suite kept passing unmodified once
  `score()` was added (checked directly, not just claimed): `git log` shows
  `pick()`'s own logic was never touched in the strategy files, only
  `score()` was appended alongside it.

## 2. Does the code match the final architecture (PRD §6)?

| Diagram element | M4 state | OK? |
|---|---|---|
| Every routing decision records its full candidate set | `CandidateScore[]` via `score()`, captured by the engine on every `route()` call, success or failure | ✅ |

## 3. A real finding from N16: `already_tried` cannot fire on the live path

`test/integration/m4.test.ts`'s header documents this, and it is worth
recording here rather than only in a test comment. The task split
(`docs/milestones/m4/task-split.md`, N16) expected a retried request's
excluded replica to show `reason: "already_tried"`. Live, it never does.

**Why:** `POST /route`'s retry loop calls `scheduler.eject(replicaId,
reason)` synchronously on every retryable failure, before looping
(`src/api/server.ts`). By the time the next `engine.route()` call runs, the
registry already reports that replica `unhealthy`. The engine filters
`healthy` before it ever checks `opts.exclude`, and N3's tie-break rule
(`unhealthy` wins when both apply, `docs/milestones/m4/shared-contract.md`)
means the exclusion always reports `unhealthy`, never `already_tried`, for
any replica this same request already tried.

`already_tried` is not dead code: it is reachable, and correctly, at the
engine level (`test/routing-engine.test.ts` calls `route({ exclude })`
directly against a replica the test deliberately keeps healthy). It is just
never reachable through the one live caller the retry loop actually is,
because that caller happens to always eject before it excludes.

**This is accepted, not fixed, for M4.** Two ways it could change in a
future milestone, neither built:
1. A future retry policy that excludes without ejecting (e.g. a
   non-retryable-but-still-worth-avoiding case) would make `already_tried`
   live-reachable.
2. `already_tried` stays purely a defensive case for a caller other than the
   M3/M4 retry loop, e.g. a future MCP tool driving `route()` directly with
   its own exclusion set.

Not treated as a bug: nothing in the PRD or the M4 definition of done
requires `already_tried` to be observable through this specific caller, only
that no replica is silently dropped from the record, which continues to
hold (every excluded replica gets a reason, just not always both possible
reasons in practice).

## 4. Leakage check: did any later-milestone concern get built in?

Grepped `src/` for `mcp`, `explain_routing_decision`, `query_decisions`,
case-insensitive.

**Zero hits in implementation.** Every hit is a comment naming a future
tool by name for context (`src/routing/config.ts`, `src/routing/types.ts`,
`src/routing/strategies/index.ts` reference `set_routing_strategy` /
`set_scoring_weights`, pre-existing since M2; `src/decisions/types.ts`
references `explain_routing_decision` / `query_decisions` as the reason the
shape looks the way it does). No MCP server, no dashboard, no
natural-language-query code exists.

- `DecisionLog.get(requestId)` exists specifically because M5a needs a point
  lookup, but it does no more than that: a linear scan, no caching, no query
  language. The shape is aimed at M5a; the implementation is M4-scoped.

## 5. Known deferrals: carry into M5, do not fix now

1. **`RegistryStore` is still synchronous** (M1 deferral 1, unchanged since
   M2/M3). First real need is M5a.
2. **`DecisionLog` is in-memory and unbounded**, same deferral shape as M3's
   failover log (`src/decisions/decision-log.ts`'s own header). Persistence
   (PRD §7: JSON lines -> SQLite) is M7/M8, once Docker/K8s exist to manage
   it.
3. **`already_tried` is unreachable through the live retry path** (§3
   above). Documented, not fixed; revisit only if a future milestone adds a
   second caller of `route({ exclude })` that doesn't eject first.
4. **`get()` is a linear scan**, same backing array as `query()`. Fine at
   demo scale; flagged as a revisit in `decision-log.ts`'s own header if
   request volume ever makes that not true.
5. **The M4 integration test builds the system in-process**, same reasoning
   and same deferral as M3's: it needs a live reference to `DecisionLog` to
   assert on recorded decisions directly, since `explain_routing_decision`'s
   HTTP surface doesn't exist yet. Revisit once M5a's real surface exists.
6. **A retried request's earlier-round failure detail lives only in
   `DecisionRound.failureReason`**, not cross-checked against the
   now-discarded HTTP `attempts` list at read time, since the whole point of
   adding the field was that the HTTP response is long gone by the time
   anyone reads the decision log. No further action needed, noting it here
   only so the reasoning for the field isn't lost.

## 6. Success metrics (PRD §8): status

M4 does not own a new PRD §8 metric directly (those are latency/loss/load
metrics, all M2/M3 territory, unchanged and already measured in the M3
review). M4's own bar is PRD §5.5's structural requirement, which §1 through
§3 above address: every decision is recorded, with a full candidate set and
an exclusion reason for everything not scored. That requirement is met and
verified end to end by `test/integration/m4.test.ts`, not just by unit
coverage of the pieces in isolation.

## 7. M4 definition of done (from the task split)

- [x] Every `POST /route` request produces exactly one `Decision`, id'd by
  its `requestId`, capturing every round the request went through
  (`test/integration/m4.test.ts`: 5 requests, 5 decisions, unique ids)
- [x] Each round's candidate set includes every candidate the strategy
  actually scored, with its score inputs at decision time
- [x] A replica excluded before scoring appears in the round's exclusion
  list with a reason, never silently omitted (with the `already_tried`
  caveat recorded in §3, which does not violate this: the replica is never
  omitted, its reason is just always `unhealthy` in practice)
- [x] `RoutingStrategy.pick()`'s existing signature and selection behaviour
  are unchanged; `score()` verified not to influence `pick()`'s outcome (N7)
- [x] The decision log is queryable by time range and by `requestId`
- [x] A retried request's decision captures every round, not only the final
  one (`test/integration/m4.test.ts`'s two-round case)
- [x] Unit + integration tests green in CI (177)
