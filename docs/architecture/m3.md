## 1. The bet: two failover paths, one hysteresis state machine

> PRD §5.4: "When a replica fails health checks or a request to it errors out,
> it is removed from the candidate pool immediately and in-flight requests are
> retried against the next-best replica. Recovery is automatic once health
> checks pass again."

**Verdict: correctly implemented.**

M2 left `POST /route` assuming its one pick always works. M3's actual bet is
that a live request failure and a health-check failure are two *inputs* to the
same state machine, not two separate mechanisms:

- `HealthScheduler.eject(replicaId, reason)` sets a replica `unhealthy`
  immediately from a live request failure, bypassing `unhealthyThreshold`
  entirely, this is what hits the PRD's <1s target for a replica carrying
  live traffic.
- The poll loop is unchanged and still the only path to `unhealthy` for a
  replica with zero traffic on it (the case `eject` can never see).
- **Both paths converge on identical recovery**: `healthyThreshold`
  consecutive clean probes, no shortcut, regardless of which path caused the
  ejection. This was verified, not just asserted: a real bug (found during the
  M3 shared-contract sign-off, PR #34) let a duplicate `eject()` call reset
  `consecSuccesses` mid-recovery, which would have let a stale request
  silently extend a real replica's downtime. Fixed and covered by a
  regression test before the retry loop (the code path that actually triggers
  duplicate ejects) was built on top of it.
- The retry loop treats `eject()`'s registry write as a side effect for the
  health system's benefit, not the mechanism it relies on to skip a replica
  on the next attempt; `exclude` is. Verified in `routing-engine.test.ts` and
  the retry-loop tests in `route-endpoint.test.ts`.

## 3. Leakage check: did any later-milestone concern get built in?

Grepped `src/` for `decision`, `mcp`, `rationale`, case-insensitive.

**Zero hits in code.** No decision-log or MCP code exists yet; the failover
log is explicitly scoped as "not the M4 decision log" in its own file header
(`src/events/failover-log.ts`), and `FailoverEvent`'s `reason` field is a
short synthesized string for the M5a timeline, not the per-request scored
candidate set M4's decision log will need.

- `attempts` on the `/route` response (`{ replicaId, kind, status? }`) is the
  closest thing to a decision record in M3, and it is scoped to one request's
  retry history, not a persisted, queryable log. M4 is a separate structure.

## 4. Known deferrals: carry into M4 / M5, do not fix now

1. **`RegistryStore` is still synchronous** (M1 deferral 1, unchanged since
   M2). First real need is M5a, when the MCP server becomes a second
   consumer.
2. **The failover log is in-memory and unbounded** (flagged in its own
   header). A demo-scale fleet produces a handful of events; persistence and
   a retention cap are M4/M5 concerns.
3. **Retrying a request means it can run twice**, on two different replicas,
   if the first attempt's response arrives after the retry already fired
   (the adapter has no cancellation). PRD §10 already accepted this trade
   (bounded retries over a zero-loss-with-no-retry guarantee); flagged again
   here because M3 is where it first becomes observable.
4. **Every 5xx is treated as equally retryable** (L1's known simplification):
   a `501`/`505` a homogeneous fleet would reject identically is retried the
   same as a transient `503`. Accepted for M3's synthetic fleet; revisit only
   if a real backend starts returning a stable, non-transient 5xx.
5. **The M3 integration test builds the system in-process rather than
   spawning `main.ts`** (unlike M1/M2's integration tests), so it can assert
   on `FailoverLog` contents directly without an HTTP surface for it (that's
   M5a). Deliberate, documented in the test's own header, and worth
   revisiting once `get_failover_history` exists and the spawn-based pattern
   becomes free again for this test too.
6. **Hysteresis thresholds (N=3, M=2) are unchanged; only the poll interval
   moved** (L7, `docs/decisions.md`). Measured on loopback only; real network
   jitter (Phase 2's real adapter, or any non-local deployment) isn't
   captured and is called out as a revisit trigger in that decision.

## 5. Success metrics (PRD §8): status

| Metric | Target | M3 status |
|---|---|---|
| Failover detection time | < 1s from replica death to traffic shed | **Measured, met.** `test/integration/m3.test.ts` asserts the recorded ejection event's timestamp lands under 1s after the kill, and that it is `trigger: "request_failure"`, not the poll backstop. Run repeatedly locally with no flakes. |
| Request loss during single-replica failure | 0 (all retried successfully) | **Measured, met.** The same integration test drives continuous load through the kill/revive arc and asserts every single response across the whole run is `200`. |
| p99 routing overhead | < 10ms added per request | **Still not measured** (carried from the M2 review). The retry loop adds at most `maxRetries` extra `sendRequest` round-trips on a failure path, not the success path measured by this metric; still needs an actual benchmark task. |
| Load distribution | No replica > 1.5x median utilization | **Still not validated for real** (carried from the M2 review, same reasoning: existing tests use deliberately uneven profiles to prove the load-aware strategies work, which is the opposite scenario from this metric). |

The two metrics M3 actually owns (failover detection, zero request loss) are
now measured and passing. The other two remain M2-era carryovers, still
instrumentation gaps, not design gaps.
